# Sources

Everything in this skill comes from primary sources, read start to finish. Not from general knowledge. The raw files sit in a local, git-ignored research cache (`.research/state-machine-design/` at the repo root) so we can go back and reread them. We never redistribute them here. Several are copyrighted academic papers, and that stays true even in a public repo.

## Foundational literature

1. Harel, D. (1987). _Statecharts: A Visual Formalism for Complex Systems._ Science of Computer Programming 8(3), 231-274. **Read in full.** The foundational paper. Hierarchy through OR/refinement, orthogonality through AND-decomposition, broadcast communication, and the state-explosion problem that started all of this.
2. Harel, D. & Naamad, A. (1996). _The STATEMATE Semantics of Statecharts._ ACM TOSEM 5(4), 293-333. **Read in full.** The first rigorous operational semantics. Step, superstep, the perfect-synchrony hypothesis, and Statemate's outside-in transition priority.
3. Harel, D. (2009). _Statecharts in the Making: A Personal Account._ HOPL III / CACM 52(3), 67-75. **Read in full.** Harel's own history of the work. The elicitation method, "what happens when...?", and his regret that roughly twenty rival semantics sprang up because the official one wasn't published fast enough.
4. Harel, D. & Gery, E. (1997). _Executable Object Modeling with Statecharts._ IEEE Computer, July 1997. **Read in full.** This paper documents the OO/Rhapsody variant reversing Statemate's own transition-priority rule, inside-out instead of outside-in. Same author, real disagreement, not just a different name for the same thing.
5. von der Beeck, M. (1994). _A Comparison of Statecharts Variants._ In Formal Techniques in Real-Time and Fault-Tolerant Systems (LNCS 863), 128-148. **Not obtained.** No open copy exists anywhere we checked: Springer, ACM DL, DBLP, Semantic Scholar, ResearchGate, CORE.ac.uk, university mirrors. We know it only secondhand, as a survey of roughly twenty statechart variants. We do not use it as the source of any specific claim here. Harel and Gery's own documented disagreement, source 4, carries that weight instead.
6. Pnueli, A. & Shalev, M. (1991). _What is in a Step: On the Semantics of Statecharts._ **Not obtained.** Same story: paywalled everywhere, no open copy at the Weizmann Research Portal or Pnueli's own publication list. It's widely described secondhand as fixing causality problems in the Statemate-style step definition. We don't attribute any claim in this skill to it.
7. Samek, M. _A Crash Course in UML State Machines._ Quantum Leaps whitepaper. **Read in full.** The practitioner's view, from the embedded-systems world. The six-step design process, the guard-abuse anti-pattern, and the real defect in the textbook guard-exit-action-entry ordering.

## Modern academic surveys

8. _Formalizing UML State Machines for Automated Verification: A Survey._ arXiv 2407.17215 (2024). **Read in full.** A review of 61 formal-verification approaches from 1997 to 2021. We use it mostly to cross-check UML's full syntax and as evidence that even run-to-completion, the most basic guarantee there is, gets implemented correctly by fewer than a third of the tools surveyed.
9. _STL4IoT: A Statechart Template Library for IoT System Design._ arXiv 2311.18175 (2023). **Read in full.** A component-reuse methodology for IoT systems, built on Statemate-derived tooling. Good evidence for the state-explosion-versus-parallel-regions math, at systems-of-systems scale.
10. Harel, D., Marelly, R., Marron, A. & Szekely, P. _Integrating Inter-Object Scenarios with Intra-Object Statecharts for Developing Reactive Systems._ arXiv 1911.10691. **Read in full.** Draws the line between the inter-object view (scenarios) and the intra-object view (statecharts) of behavior. We didn't build it into the methodology directly, that's a single-object process, but it confirms this inter/intra framing is live in Harel's own later work.

## Standard

- W3C Recommendation, _State Chart XML (SCXML): State Machine Notation for Control Abstraction_, https://www.w3.org/TR/scxml/ (1 September 2015). **Read in full**, section by section, including the formal algorithm in Appendix D. This is the closest thing we have to an industry standard, and it anchors this skill's vocabulary: configuration, `cond`, datamodel, microstep and macrostep, and the exact semantics for history states and a parallel state being "done."

## Engine and library documentation, read start to finish

- **XState** (JS/TS), stately.ai/docs. The most complete modern open-source implementation. Source of the actor-model vocabulary, actor, invoke, spawn, and the clearest stated design heuristics we found anywhere: the behavior-driven state boundary test, "start flat, refactor to hierarchy."
- **Spring Statemachine** (Java), reference docs. A full UML-equivalent implementation, with a configurable transition-conflict policy (see below) and explicit sequential-versus-parallel region execution.
- **Stateless** (.NET/C#), github.com/dotnet-state-machine/stateless. Confirms the "standard feature floor," hierarchy, guards, entry and exit actions, by what it deliberately leaves out: no parallel regions, no true history state, both by stated design, not by accident.
- **python-statemachine** (Python), python-statemachine.readthedocs.io. Full statechart support, compound, parallel, history, with eager structural validation at class-definition time.
- **`transitions`** (Python), github.com/pytransitions/transitions. The deliberately minimal counterpoint to python-statemachine. No static validation. Hierarchy bolted on as a string-concatenation extension, not built in.
- **Erlang/OTP `gen_statem`**, erlang.org/doc. The actor-model contrast case. No native hierarchy, no parallel regions, none at all. This is where the State/Data separation rule comes from: if a change in this data would change which events get handled, it belongs in the state, not the data.
- **Robot** (JS, about 1KB), thisrobot.life. Rejects parallel states and native hierarchy outright, as a size and simplicity tradeoff. Models nesting by invoking a separate machine instead.
- **statecharts.dev** (statecharts.github.io), a cross-engine educational reference. We used it to sanity-check the whole glossary. Its "How to use statecharts" page is one of the only sources with a named, explicit design process: scope, then distill the event/guard/action/state API, then find the top-level modes, then iterate with substates.

## Visualization tooling

- **Mermaid** `stateDiagram-v2`. Checked directly against mermaid.js.org's own syntax reference. Confirmed: hierarchy works, parallel regions (`--`) work, choice pseudostates (`<<choice>>`) work. Confirmed: history pseudostates do not work at all. Zero support. That single gap is why a history state forces you past the static Mermaid tier. See [VISUALIZATION-FORMAT.md](VISUALIZATION-FORMAT.md).
- **`state-machine-cat`** (github.com/sverweij/state-machine-cat). A diagramming tool built specifically for statecharts, not generic UML, with native history (shallow and deep), native parallel regions, native choice/fork/join, and native SCXML import and export. We verified it ourselves while building this skill: `npx state-machine-cat` rendered a combined hierarchy-plus-parallel-plus-history example to a valid SVG, falling back to a bundled wasm renderer with no system Graphviz install needed.
- **PlantUML**. Also confirmed, through its own official docs and not secondhand forum claims that turned out wrong, to support history (`[H]`/`[H*]`), concurrent regions (`--`/`||`), and fork/join. We didn't pick it as the primary tier-two tool because it needs a JVM, and this is an npm-oriented repo. `state-machine-cat`'s vocabulary already matches this skill's SCXML-anchored glossary more closely anyway. Worth trying if `state-machine-cat` or npx isn't available but Java is.

## Terminology conflicts

- **Transition priority direction is a real fight.** SCXML, XState, and the OO/Rhapsody statecharts variant (Harel and Gery, 1997) all give priority to the more specific, innermost state when transitions conflict across a hierarchy boundary. The original Statemate semantics (Harel and Naamad, 1996) gave priority to the outermost state instead, a documented reversal between the same author's own 1996 and 1997 papers. Spring Statemachine makes this a config option (`transitionConflictPolicy: CHILD | PARENT`), because both conventions are alive in production right now. [GLOSSARY.md](GLOSSARY.md) picks the modern, innermost-first convention, and flags it as engine-dependent.
- **"Step" means opposite things depending on who wrote it.** Statemate's own "step" is SCXML's "microstep." Statemate's "superstep" is SCXML's "macrostep." GLOSSARY.md uses SCXML's names.
- **Guard versus condition, action versus callback: naming only.** python-statemachine and `transitions` call the exact same thing "condition" and "callback" in their own APIs. No semantic difference. GLOSSARY.md picks guard and action, lists the synonyms.
- **Hierarchy and parallel regions aren't universal, and that's not a flaw in the ones that skip them.** SCXML, Harel's original paper, XState, Spring, and python-statemachine treat them as fundamental. Stateless, `transitions` without its extension, Robot, and the whole actor-model lineage (`gen_statem`) leave them out on purpose. Two different problems, UI and component behavior versus backend process and message handling, not one camp getting it wrong. See step 12 in [METHODOLOGY.md](METHODOLOGY.md).
