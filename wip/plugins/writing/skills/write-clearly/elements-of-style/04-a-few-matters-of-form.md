# Matters of form

Use the format that best exposes the information. Follow the repository's formatter and documentation conventions when they specify a form.

## Headings

Use headings to identify real topics or stages. Prefer sentence case unless local style requires another form. Leave a blank line after each heading.

Do not create a heading for a single sentence when the sentence fits naturally in the surrounding section.

## Lists

Use a list for parallel items, choices, requirements, or steps. Use prose for a connected explanation.

Make list items grammatically parallel. Use numbered lists only when order matters or later text refers to item numbers.

Do not convert every paragraph into bullets. Excessive lists hide relationships between claims.

## Numerals, dates, and units

Use numerals for measurements, versions, dates, times, limits, status codes, and exact counts. Include units with values when the unit is not fixed by the field or type.

- `250 ms`
- `HTTP 429`
- `2026-08-21`
- `3 retries`

Use one date and time format consistently. Include the time zone when an instant could otherwise be interpreted locally.

## Code and identifiers

Format identifiers, literals, commands, file names, and syntax as code. Preserve exact spelling and case.

> Set `retryAfterMs` to `null` when the response has no valid delay.

Do not replace a precise identifier with a synonym when the identifier helps the reader connect prose to code.

## Quotations

Quote a source when its exact wording matters. Paraphrase when only the fact matters, and preserve the source's level of certainty.

Introduce a block quotation with enough context to identify the speaker or source. Do not use a quotation as a substitute for explaining its relevance.

## Parentheses and dashes

Use parentheses for secondary information that remains useful. Integrate essential conditions into the sentence.

Use dashes sparingly for interruption or emphasis. A comma, period, or parentheses usually states the relationship more precisely.

## Links and references

Link evidence that a reader may need to verify or apply the claim. Use descriptive link text.

Keep dated research trails, package investigations, and audit evidence in the record that maintains them. Put only the resulting current contract in ordinary API documentation.

## Tables

Use a table when readers must compare several items across the same fields. Use a list when each item needs only one fact.

Keep cell contents short. If a cell requires several paragraphs, the information probably needs separate sections.

## Emphasis

Use structure and word order before bold or italics. Reserve visual emphasis for information that a reader must notice during scanning.

Do not bold routine nouns, every list label, or claims that should be clear from their wording.

## Examples

Label examples by the distinction they demonstrate, not with generic names such as “Example usage.” Keep the example close to the rule it clarifies.
