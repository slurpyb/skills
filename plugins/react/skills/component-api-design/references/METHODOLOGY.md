# Methodology

A general process for designing a component's public API, built by studying how real, widely-used component libraries actually name things, not by inventing conventions from scratch. Use the terms in [GLOSSARY.md](GLOSSARY.md) exactly. Two steps below, controlled/uncontrolled props and callbacks, have their own dedicated guides: [CONTROLLED-UNCONTROLLED.md](CONTROLLED-UNCONTROLLED.md) and [CALLBACKS.md](CALLBACKS.md).

## 1. Name the component and its anatomy first

Before any code, write down the parts: trigger, content, item, positioner, whatever this component actually needs. Group related parts with a shared prefix (`item`, `itemText`, `itemIndicator`) and shared roles with a shared suffix (`itemTrigger`, `closeTrigger`, `clearTrigger`, all end in `Trigger`). camelCase in code, kebab-case once it hits the DOM.

You have a real choice here, not just a style preference. Some systems make anatomy an explicit, declared artifact, one schema producing every part's selector and DOM attributes at once, and the whole public API falls directly out of that declared list. Others leave anatomy implicit in JSX structure instead. The declared version scales better across a whole library of components and stays introspectable at the type level. The implicit version is faster to reach for on a single component. Pick the declared version once you have more than a handful of components sharing conventions; pick implicit for something small and self-contained.

## 2. Decide what Root actually renders

Two shapes, and the component's own nature decides which one you need. A structural component, an accordion, a select, a tabs widget, has a real DOM footprint at the top level, so Root renders a wrapper element. An overlay or portal component, a dialog, a popover, its content lives somewhere else in the tree entirely, usually a portal, so Root is a pure state provider with no DOM output of its own. Don't force a DOM wrapper onto something that's going to be portalled away from that exact spot anyway.

## 3. Design the compound export shape

Land on `Namespace.Part` (`Dialog.Root`, `Dialog.Trigger`) either way. The real decision is how you get there. Export each part under its own fully-qualified name (`DialogTrigger`) from its own module, then also re-export the whole set under a namespace object (`export * as Dialog`). This gives callers both `Dialog.Trigger` and `DialogTrigger`, qualified names show up cleanly in devtools and error messages, and the namespace object is what's actually pleasant to type. Skipping the namespace object and shipping flat qualified names only is a real option too, when you're optimizing for a codebase people read and edit directly rather than one they import as a black box.

## 4. Design every stateful prop as a controlled/uncontrolled triad

`value`, `defaultValue`, `onValueChange`. `open`, `defaultOpen`, `onOpenChange`. All three, every time, no exceptions. This is the single most universal convention in component API design, and it deserves its own guide: [CONTROLLED-UNCONTROLLED.md](CONTROLLED-UNCONTROLLED.md).

## 5. Design the callback payload shape, once, for the whole surface

Bare positional value or a details object, decide once and hold it everywhere across the whole component (and ideally the whole library). Mixing both inside one surface is the mistake to avoid. Full guide, including naming, firing rules, and granularity, in [CALLBACKS.md](CALLBACKS.md).

## 6. Decide the polymorphism strategy, and don't mix mechanisms

Pick one of two real architectures, not a spectrum:

- **Clone-based** (`asChild`/Slot): the part clones its single child element and merges props onto it. Simple, purely structural, can't see internal component state, requires exactly one child.
- **Render-function-based** (a `render` prop): accepts an element (same prop/ref merging as clone-based) or a function `(props, state) => element` that receives the part's actual internal state. Strictly more capable, at a real cost: the eventual DOM tag isn't knowable before hydration when this swaps elements, so you need an escape hatch (something like a `nativeButton` prop) to know which default behaviors still apply.

Whichever you pick, the consumer contract (forward the ref, spread the props) has to be written down somewhere a caller will actually see it, not left implicit.

## 7. Design data-attributes for every meaningful state

Every state that could plausibly drive a CSS rule gets a data-attribute. Two decisions to make on purpose, not by accident:

**Addressing scheme.** Bespoke, hand-written attributes per component are the fastest to reach for on a single component. A generic two-key scheme, a scope key plus a part key, generated by one shared factory, is worth the setup cost once you have a whole library of components that need the same selector strategy to work identically everywhere. A single component-identity key is enough when the codebase is small and grep-able and you own every line of it.

**Enum vs. boolean-per-state.** A single enum attribute (`data-state="open"|"closed"`) is terser to read at a glance. Separate boolean attributes per state (`data-open`, `data-closed`) let two states coexist without an enum forcing a single value, which matters the moment you need something like "open" and "still animating in" to both be true.

Whatever you pick, render every boolean the same way, with no exceptions: present when true, absent when false (`data-disabled={cond ? '' : undefined}`), never the literal strings `"true"`/`"false"`.

## 8. Design CSS custom properties for anything that needs a measured value

Widths, heights, transform origins, computed positions, anything the component has to measure in JS belongs in a CSS variable, set inline. Name it one of two ways: fully-qualified per component, per part, per property, which never collides even when several different popup components sit composed on one page, or generic and shared across every component that needs the same kind of value, which is DRY and only safe because each variable is always scoped to one positioning element and never read globally. More components sharing the same positioning primitive pushes you toward generic names; components composed together on a page pushes you toward fully-qualified ones.

## 9. If this ships pre-styled, design a variant vocabulary explicitly

Headless components don't have this problem. The moment you ship opinionated visual styling, name the axes (`variant`, `size`) and the values on each axis as a real, closed vocabulary, not whatever felt right per component. Mirror whichever variant is active back onto the DOM as its own data-attribute (`data-variant`, `data-size`), so custom CSS can target it without re-deriving the value from a className string. And always accept a `className` prop and merge it last, so a consumer's override wins over your defaults, never the other way around.

## 10. Decide the escape hatches on purpose, not as afterthoughts

Three show up repeatedly, and each solves a real, specific problem rather than being generic flexibility for its own sake:

- **An `ids` prop**, overriding every internal DOM id by part name, exists specifically so two separate component instances can be composed to share a relationship (a tooltip anchored to a popover's trigger) without either one needing to know about the other's internals.
- **A Root/Provider split** (or a scope mechanism) exists for callers who need to build the underlying state themselves, outside the normal tree, then hand it down, or who need to re-parent one primitive inside another's tree without id or context collisions.
- **An imperative handle or actions ref** exists for control that genuinely can't be expressed declaratively, closing a dialog only after an external animation finishes, for instance. Don't reach for this before you have a concrete case declarative props can't cover.

## 11. Write the governing philosophy down, once, and let it settle every close call

Every well-designed component API can state its own principle in one sentence, and that sentence is what actually resolves ambiguous naming decisions, not a style guide. Something like: ship unstyled, expose every meaningful state as a data-attribute so any styling system can hook into it. Or: encapsulate logic and accessibility, give the caller full, unopinionated control over styling. Or: the code is the consumer's now, optimize for a person reading and editing that exact file, not for a stable long-term contract nobody will ever see.

Decide which principle actually governs the thing you're building, write it down in one sentence, and use it to break every tie the rest of this methodology leaves open.
